# Library Business Rules

This document describes the business rules currently modeled by the library test context.

The context model is maintained by `spec/js/dal.js`. The test behavior is generated by `spec/js/lib_stories.js`, and the REST calls and verification helpers are defined in `spec/js/interfaces.library.js`.

## Main Entities

### User

A user represents a library member.

Rules:

- A user can be created independently. The story supplies a virtual id and the SUT assigns the
  real id returned by the create response.
- A user can be deleted only when the user has no active loans and no active holds.
- If a user has an active loan, deleting that user is expected to fail with `400`.
- After a successful user deletion, the user should not appear in users, loans, or holds lists.
- Deleting a user that no longer exists is expected to fail with `404`.

Context queries:

- `User.All`
- `User.CanDelete`
- `User.CannotDelete`

## Book

A book represents a library item.

Rules:

- A book can be created independently. Only `title` is client-supplied; the SUT assigns the
  book's `id` itself, so there is no client-chosen id to duplicate.
- A book can be deleted only when the book has no active loans and no active holds.
- After a successful book deletion, the book should not appear in books, loans, or holds lists.
- Deleting a book that no longer exists is expected to fail with `404`.

Story behavior:

- Stories and the DAL address every entity by its virtual id. Each successful create callback
  stores the SUT id in a Provengo run-time variable (`USERn`, `BOOKn`, or `HOLDn`; a loan is
  addressed by its user/book pair and needs none). The
  interface layer uses late-bound `@{...}` expressions wherever an id is sent in a URL, body, or
  query parameter.

Context queries:

- `Book.All`
- `Book.CanDelete`
- `Book.CannotDelete`

## UserBook

`UserBook` is the context relation between a user and a book.

For every existing user and every existing book, the DAL creates a `user-book` entity. This gives the stories a simple way to ask questions about valid user/book pairs.

Rules:

- When a new user is created, the DAL creates `user-book` rows for that user with all existing books.
- When a new book is created, the DAL creates `user-book` rows for that book with all existing users.
- When a user is deleted, all `user-book` rows for that user are removed.
- When a book is deleted, all `user-book` rows for that book are removed.

Context queries:

- `UserBook.All`
- `UserBook.CanCreateLoan`
- `UserBook.CannotCreateLoan`
- `UserBook.CanCreateHold`
- `UserBook.CannotCreateHold`

## Loans

A loan connects one user to one book.

Rules:

- A loan can be created only when the user has no active loan and the book has no active loan.
- A user cannot have more than one active loan.
- A book cannot have more than one active loan.
- A second successful loan creation for the same user or the same book is blocked while the original loan exists.
- If a loan already exists for the user or the book, trying to create another loan is expected to fail with `400`.
- A loan can be deleted when it exists.
- After a successful loan deletion, the loan should not appear in the loans list.
- Deleting a loan that no longer exists is expected to fail with `404`.

Context queries:

- `Loan.All`
- `UserBook.CanCreateLoan`
- `UserBook.CannotCreateLoan`

Story behavior:

- `createLoan` creates valid loans from `UserBook.CanCreateLoan`.
- `verifyCannotCreateLoan` verifies that a loan for a busy user or book fails with `400`.
- `verifyCannotCreateLoanWithNonexistent{User,Book,UserAndBook}` verify that a loan whose user
  and/or book does not exist fails with `400` (once per book, once per user, once per run).
- `deleteLoan` deletes existing loans from `Loan.All`.
- `verifyLoanDeletion` reads the loans list and re-deletes the loan (expecting `404`) after each
  deletion, unless the same pair was loaned again in the meantime.

Trace format:

```text
Create a loan <loan-number> <user-id>/<book-id>
Delete a loan <loan-number> <user-id>/<book-id>
```

Example:

```text
Create a loan 609009 587/391
Delete a loan 609009 587/391
```

## Holds

A hold connects one user to one book request. Holds are queue-style reservations: a user can request a book even when that book is currently loaned.

Rules:

- A hold can be created for any existing user/book pair, even when the book is currently loaned.
- A user may have multiple active holds.
- A book may have multiple active holds.
- The same user/book pair may have multiple active holds when each hold has a unique hold number.
- A duplicate hold number is expected to fail with `400`.
- A hold can be deleted when it exists.
- After a successful hold deletion, the hold should not appear in the holds list.
- Deleting a hold that no longer exists is expected to fail with `404`.

Context queries:

- `Hold.All`
- `UserBook.CanCreateHold`
- `UserBook.CannotCreateHold`

Story behavior:

- `createHold` creates valid holds from `UserBook.CanCreateHold` (every existing user/book
  pair, loaned or not).
- `verifyCannotCreateHoldWithNonexistent{User,Book,UserAndBook}` verify that a hold whose user
  and/or book does not exist fails with `400` (once per book, once per user, once per run).
- `deleteHold` deletes existing holds from `Hold.All`.
- `verifyHoldDeletion` reads the holds list and re-deletes the hold (expecting `404`) after each
  deletion.

Trace format:

```text
Create a hold <hold-number> <user-id>/<book-id>
Delete a hold <hold-number> <user-id>/<book-id>
```

Example:

```text
Create a hold 640626 587/391
Delete a hold 640626 587/391
```

## Loan and Hold Relationship

Loans and holds are related through the book.

Rules:

- If a book has an active loan, creating a hold for that book is allowed.
- If a book has an active loan, the book cannot be deleted.
- If a user has an active loan, the user cannot be deleted.
- If a book has active holds, the book cannot be deleted.
- If a user has active holds, the user cannot be deleted.
- Deleting a user or book removes the matching context state for user-book rows, loans, and holds after a successful delete event.

## Context State Changes

The DAL updates the context only after events that are expected to succeed.

Rules:

- `POST` events update the context only when the event expects `201`.
- `POST` events expecting `400` or `404` are verification attempts and do not create context entities.
- `DELETE` events update the context only when the event expects `200`.
- `DELETE` events expecting `400` or `404` are verification attempts and do not remove context entities.

This prevents negative verification calls from corrupting the expected model.

## Current Important Assumptions

- The current loan rule is strict: one active loan per user and one active loan per book.
- The current hold rule is queue-style and flexible: a user can have multiple active holds, a book can have multiple active holds whether or not it is loaned, and the same user/book pair can have multiple active holds when each hold has a unique hold number.
- Hold numbers are unique identifiers for hold deletion.
- Loan numbers are used for trace descriptions, while the loan identity in the SUT is the `userId/bookId` pair.

## Read Behavior

Rules:

- `GET /books/{id}`: a malformed, zero, or negative `id` is rejected with `400`. A well-formed
  `id` for a book that does not exist returns `404`. A well-formed `id` for a book that exists
  returns `200` with the book body.
- `GET /loans` filters by the `userId`/`bookId` query parameters when present; a malformed, zero,
  or negative value for either is rejected with `400`.
- `GET /books`, `GET /users`, and `GET /holds` filter by the free-text `q` query parameter, which
  is never validated: any value, including malformed or empty strings, returns `200`.

Story behavior:

- `verifyBookDetailExists` reads `GET /books/{id}` once and expects `200`.
- `verifyBookExists`, `verifyUserExists`, `verifyLoanExists`, and `verifyHoldExists` read the
  matching SUT list once and expect `200`.
- After a successful book deletion, `GET /books/{id}` for the deleted id is expected to return
  `404`.

## Interface Layer Contract

Every action function in `interfaces.library.js` sends exactly one REST request: one call in a
story is one event in the trace. Negative checks (`tryTo*AndExpectError`) cover business-rule
rejections only: deletes blocked by an active loan or hold, loans the rules forbid, and entities
that do not exist or were already deleted. The model never sends a malformed request (missing
fields, wrong types, nulls, zero or negative ids) and never calls an unsupported route such as
`PUT`. The SUT's input-validation rules below are documented for reference only.

## Parameter and Type Rules

To support flexible integrations, SUT endpoints allow several valid options for entity IDs in request bodies. This section covers ids the client actually sends - it does not apply to a book's own `id`, which the SUT assigns (see the Book section above).
- **Valid ID formats**: IDs (such as `id`, `userId`, `bookId`) can be passed as either a positive integer (e.g. `123`) or a string representing a positive integer (e.g. `"123"`).
- **Parameter ordering**: The order of keys in JSON request bodies is flexible and does not affect validation.
- **Invalid ID formats**: Passing IDs as non-integer/non-numeric-string types, such as objects (e.g., `{"val": 123}`), arrays, booleans, or null, is invalid and expected to fail with `400`.
- **Unrecognized fields**: All four `POST` create endpoints (`/users`, `/books`, `/loans`, `/holds`)
  read only their documented required fields and silently ignore anything else in the body -
  an unexpected field never causes a `400`.

## ID Generation

Server-owned ids (`/users`, `/books`, `/loans`, `/holds` create responses) are assigned from a
per-entity-type monotonic counter that only ever increases (see `_next_ids`/`generate_unique_id`
in `sut.py`). Deleting an entity never frees its id for reuse - the next created entity of that
type always gets a strictly higher id than any previously issued, leaving a permanent gap where
the deleted one was. This matters for the RTV mechanism in `interfaces.library.js`: an RTV entry
(`USERn`/`BOOKn`/`HOLDn`) recorded at creation stays a valid, permanent reference to that
specific real id for the rest of the run, even after the entity is deleted - it can never later
resolve to some other, unrelated entity that happens to reuse the same real id.
