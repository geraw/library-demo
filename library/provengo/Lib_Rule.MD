# Library Business Rules

This document describes the business rules modeled by the library test context and the stories
that exercise them.

The context model is maintained by `spec/js/dal.js`. The test behavior is generated by
`spec/js/lib_stories.js`. The REST calls, EventSets and event-data extraction are in
`spec/js/interfaces.library.js`; generic helpers (description builders, event accessors, list
reads) are in `lib/utils.js`.

## Identity

Stories, EventSets and the DAL address every entity by a small logical id that the story picks
when it asks for creation (`User 2`, `Book 3`, `Hold 4`, `Loan 2/3`). The service assigns its own
ids. Each successful create callback stores the service id in a Provengo run-time variable
(`USERn`, `BOOKn`, `HOLDn`; a loan is addressed by its reader/book pair and needs none), and the
interface layer uses late-bound `@{...}` expressions wherever a service id goes in a URL, body
or query parameter. Ids that are deliberately never created (1000000001 and up) are sent as
plain values; they cannot collide with a service id.

Every event, rejection checks included, carries its logical ids in the REST `parameters` (`id`,
or `userId`/`bookId`) together with a `description` that is the trace line. Ids are derived,
never counted: readers and books are numbered by the single b-thread that creates them, a hold's
id is derived from its reader/book pair and from how many holds that pair created before (so it
never repeats), a loan has no id of its own, and a never-created id is 1000000000 plus the id of
the entity on the other side (or a small constant for the once-per-run checks). The trace is
therefore a function of the selected events alone, not of the scheduling of b-threads.

## Main Entities

### User

A user represents a library member (a reader).

Rules:

- A user can be created independently.
- A user can be deleted only when the user has no active loans and no active holds; otherwise
  the delete is rejected with `400`.
- After a successful user deletion, the user does not appear in the users, loans or holds lists.
- Deleting a user that no longer exists, or never existed, is rejected with `404`.

Context queries: `User.All`, `User.CanDelete`.

### Book

A book represents a library item.

Rules:

- A book can be created independently. Only `title` is client-supplied; the service assigns
  the book's id.
- A book can be deleted only when the book has no active loans and no active holds; otherwise
  the delete is rejected with `400`.
- After a successful book deletion, the book does not appear in the books, loans or holds
  lists, and `GET /books/{id}` for it answers `404`.
- Deleting a book that no longer exists, or never existed, is rejected with `404`.

Context queries: `Book.All`, `Book.CanDelete`.

### UserBook

`UserBook` is the context relation between a user and a book. For every existing user and every
existing book the DAL keeps a `user-book` entity, so stories can ask which pairs may be loaned
or held.

Rules:

- When a user is created, the DAL creates `user-book` rows for that user with all existing books.
- When a book is created, the DAL creates `user-book` rows for that book with all existing users.
- When a user or a book is deleted, its `user-book` rows are removed.

Context queries: `UserBook.All`, `UserBook.CanCreateLoan`, `UserBook.CannotCreateLoan`,
`UserBook.CanCreateHold`.

### Loans

A loan connects one user to one book. Its identity in the service is the reader/book pair.

Rules:

- A loan can be created only when the user has no active loan and the book has no active loan
  (the original service's rule; the experiment contract in `../sut/README_ISSTA_BUGS.md` drops
  the per-user part, and the campaign harness patches `UserBook.CanCreateLoan` accordingly).
- While a loan is active, another loan for the same book, or for the same pair, is rejected
  with `400`; under the original rule a second loan for the same reader is rejected too.
- A loan for a reader or a book that does not exist is rejected with `400`.
- A loan can be deleted (returned) when it exists; after that the pair can be loaned again.
- Returning a loan that no longer exists, or never existed, is rejected with `404`.

Context queries: `Loan.All`, `UserBook.CanCreateLoan`, `UserBook.CannotCreateLoan`.

### Holds

A hold connects one user to one book request. Holds are queue-style reservations: a user can
request a book even when that book is currently loaned.

Rules:

- A hold can be created for any existing user/book pair, loaned or not.
- A user may have several active holds; a book may have several active holds.
- A hold for a reader or a book that does not exist is rejected with `400`.
- A hold can be deleted (cancelled) when it exists.
- Cancelling a hold that no longer exists, or never existed, is rejected with `404`.

Context queries: `Hold.All`, `UserBook.CanCreateHold`.

### Loans, holds and deletion

- A book with an active loan or an active hold cannot be deleted.
- A user with an active loan or an active hold cannot be deleted.
- Deleting a user or a book removes the matching `user-book` rows, loans and holds from the
  context after the successful delete event.

## Context State Changes

The DAL updates the context only after events that are expected to succeed:

- `POST` events update the context only when the event expects `201`.
- `DELETE` events update the context only when the event expects `200`.
- Events expecting `400` or `404` are rejection checks and never touch the context.

## Interface Layer Contract

Every function in `interfaces.library.js` sends exactly one REST request: one call in a story
is one event in the trace. Rejection checks (`tryTo*AndExpectError`,
`verifyMissingEntityReadIsRejected`) cover business-rule rejections only: deletes blocked by a
loan or hold, loans the rules forbid, and entities that do not exist or were deleted. The model
never sends a malformed request (missing fields, wrong types, nulls, zero or negative ids) and
never calls a route the service does not expose. Ids in request bodies are late-bound
references inside JSON strings (`"userId":"@{USER2}"`), so the service receives numeric strings
(never-created ids are plain JSON numbers); a body must be valid JSON before substitution or the
sampler ends the scenario there.

Every read checks the response contents with a REST callback that runs at actuation time and
compares the response with the service ids recorded at creation (`pvg.rtv.get`): a list read
after a create must contain the entity (`Verify: Book 3 is listed in books`), a list read after
a delete must not (`Verify: Book 3 is absent from loans`), a loan read must return exactly the
loan of that pair, and the book detail read must return that book (`Verify: Book 3 exists (book
detail)`). A failed check fails the scenario the same way an unexpected status code does.

## Stories

Creation:

- `createUsers`, `createBooks` create `NUMBER_OF_USERS` readers and `NUMBER_OF_BOOKS` books.
- `createLoan` loans every pair in `UserBook.CanCreateLoan`; `createHold` holds every pair in
  `UserBook.CanCreateHold`.

Deletion (the sampler is eager to delete; see the note in `lib_stories.js`):

- `deleteUser`, `deleteBook` delete every entity in `User.CanDelete` / `Book.CanDelete`.
- `deleteLoan`, `deleteHold` return every loan and cancel every hold.

Checks after creation (one b-thread per entity):

- `verifyUserExistsAfterCreation`, `verifyBookExistsAfterCreation`, `verifyLoanExists`,
  `verifyHoldExistsAfterCreation` read the matching list.
- `verifyBookDetailExistsAfterCreation` reads `GET /books/{id}`.

Checks after deletion (one b-thread per deletion event, each check independent):

- `verifyUserAbsentFrom{Users,Loans,Holds}AfterDeletion`,
  `verifyBookAbsentFrom{Books,Loans,Holds}AfterDeletion`, `verifyLoanAbsentAfterDeletion`,
  `verifyHoldAbsentAfterDeletion` read the lists.
- `verifyDeletedBookDetailIsRejected` expects `404` from `GET /books/{id}`.
- `verifyDeleted{User,Book,Loan,Hold}CannotBeDeletedAgain` expect `404` from a repeated delete.
  For loans the checks stop if the same pair is loaned again first.
- `verifyDeletedUserCannot{Loan,Hold}`, `verifyDeletedBookCannotBe{Loaned,Held}` expect `400`
  from a loan or hold that names the deleted entity, paired with whichever counterpart exists
  (skipped when none is left).

Business-rule rejections:

- `verify{Loan,Hold}Blocks{User,Book}Deletion`: one check per blocking relation, re-issued after
  every change to the loans and holds, so a rejection stays reachable after another relation
  was removed while this one remains.
- `verifyCannotCreateLoan`: a loan for a pair in `UserBook.CannotCreateLoan` is rejected,
  re-issued after every change to the loans.
- `verifyCannotCreate{Loan,Hold}WithNonexistent{User,Book,UserAndBook}`: once per book, once per
  user, once per run.
- `tryToDeleteNonexisting{User,Book,Loan,Hold}`: once per run, with never-created ids.

## Trace Format

```text
Create: User 2
Create: Book 3
Create: Loan 2/3
Create: Hold 7 for User 2 and Book 3
Verify: Loan 2/3 is listed in loans
Verify: Book 3 exists (book detail)
Verify: delete User 2 is rejected because the reader has a loan or a hold
Verify: create Loan 2/3 is rejected because the book is on loan
Delete: Loan 2/3
Delete: Hold 7 for User 2 and Book 3
Verify: User 2 is absent from users
Verify: read Book 3 is rejected because the book no longer exists
Verify: create Hold for User 2 and Book 3 is rejected because the reader no longer exists
Verify: delete Hold 7 is rejected because the hold no longer exists
Verify: delete User 1000000001 is rejected because the reader does not exist
```

## Service Id Generation

The service issues random six-digit ids per entity type and never reuses one (`sut.py`,
`generate_unique_id`). A run-time variable recorded at creation therefore stays a valid
reference to that entity for the rest of the run, even after it was deleted; it can never
resolve to an unrelated entity that reused the id. The service accepts ids as integers or as
numeric strings; the model sends numeric strings in bodies (see the contract above), plain
numbers for never-created ids, and plain integers in paths.
