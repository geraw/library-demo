# מיפוי באגים לשתילה — Library Management System (sut_type.py)

מסמך זה ממפה את **כל** הבאגים האפשריים שניתן לשתול (Mutation Testing) במערכת, לצורך תכנון בדיקות שליליות/רגרסיה. המיפוי מבוסס על קריאה מלאה של הקוד וכולל את כל השדות, כל ה-API-ים, וכל השילובים ההגיוניים והלא-הגיוניים ביניהם.

**ישויות במערכת:** User `{id, name}`, Book `{id, title}`, Loan `{userId, bookId}`, Hold `{id, userId, bookId}`
**Endpoints:** `/reset`, `/users` (POST/GET/DELETE), `/books` (POST/GET/DELETE/GET-by-id), `/loans` (POST/GET/DELETE), `/holds` (POST/GET/DELETE)

## רמה 3 — באגים משילובי קריאות "הגיוניים" (Flows סבירים)

הרצף הבסיסי: **צור יוזר → צור ספר → בקש hold → בצע loan → מחק את ה-hold/בצע return (מחיקת loan) → מחק יוזר/ספר**. גם חזרות סבירות (למשל כמה בקשות loan/hold על ספרים שונים) נכללות.

| # | תרחיש (רצף) | באג פוטנציאלי לשתילה | תוצאה |
|---|---|---|---|
| 3.1 | User→Book→Hold→Loan (על אותו ספר/יוזר) | הסרת קשר בין hold ל-loan — `add_loan` לא בודק ואינו סוגר holds קיימים | ה-hold נשאר "פתוח" גם אחרי שהספר כבר הושאל בפועל, ומונע מחיקת ספר/יוזר ("Cannot delete book with active holds") גם כשההשאלה כבר הסתיימה כי לא נמחק ה-hold |
| 3.2 | Hold על ספר → Loan לאותו ספר ע"י יוזר **אחר** | היעדר בדיקה ש-loan לא יכול להיווצר לספר עם hold פעיל של יוזר אחר | ספר עם hold של יוזר A מושאל בפועל ליוזר B — עוקף את מטרת ה-hold |
| 3.3 | Loan → DELETE loan (return) → DELETE book | שתילת באג ב-`delete_loan` שמוחק loan רק חלקית (למשל `and` הופך ל-`or`, ראו 2.44) | מחיקת ספר ש"עדיין מושאל" תיכשל / ספר לא קשור יינזק |
| 3.4 | Loan → DELETE loan → Loan מחדש על אותו userId+bookId | הסרת האיפוס/בדיקה כלשהי שמאפשרת יצירת loan זהה שוב לאחר מחיקה | אם קיים באג ב-2.38 (הסרת "Loan already exists"), loan כפול "ישן" שלא נמחק כראוי ייווצר לצד החדש |
| 3.5 | User A עושה Hold על ספר X, User B מנסה Hold על אותו ספר X | היעדר קשר בין הבדיקה ל-book_exists בלבד (אין מניעה קיימת מספר holds על אותו ספר — זהו כבר behavior תקין; אפשר לשתול "תיקון" שגוי שחוסם holds מרובים כשלא אמור) | תרחיש תור-המתנה (multiple holds) יישבר אם ייחסם בטעות |
| 3.6 | Loan נכשל כי הספר כבר מושאל (2.40 קיים כרגיל) → ניסיון Hold על אותו ספר | שתילת באג שגורם ל-`book_exists` להחזיר False בטעות אחרי loan (ערבוב בין book_exists ל-book "available") | Hold ייכשל בטעות עם "Book does not exist" |
| 3.7 | DELETE user שיש לו hold בלבד (בלי loan) | הסרת בדיקת holds ב-`delete_user` (2.12) | יוזר עם hold פעיל יימחק, וה-hold יישאר "יתום" ומצביע ל-userId לא קיים — ישפיע גם על ניסיון עתידי למחוק את הספר (חסימה שגויה כי עדיין "יש hold") |
| 3.8 | DELETE book שיש לו loan פעיל, ואז ניסיון ליצור loan חדש לאותו bookId (אחרי שהמחיקה נכשלה כמצופה) | וידוא ש-book עדיין קיים אחרי כשל מחיקה — שתילת באג שמוחק את הספר חלקית למרות ה"כישלון" המדווח (למשל מוחזר 400 אבל `books = [...]` בכל זאת מבוצע לפני הבדיקה) | חוסר atomicity: תגובת API אומרת "נכשל" אך הפעולה בוצעה בפועל |
| 3.9 | צור 2 יוזרים, 2 ספרים, השאלה צולבת (User1↔Book1, User2↔Book2), מחיקת User1 | היפוך userId/bookId בבדיקת active loans (2.11) | User1 יימחק בטעות למרות loan פעיל (כי הקוד בודק bookId==user_id ולא ימצא) — ואילו User2 ייחסם ללא סיבה |
| 3.10 | Hold → Loan → DELETE hold (ניסיון "לבטל hold" אחרי שכבר הושאל בפועל) | חוסר וולידציה שה-hold עדיין רלוונטי; שתילת באג ב-delete_hold שמוחק hold שגוי (2.56/2.57) | מצב לא עקבי: holds/loans לא מסונכרנים |
| 3.11 | רצף מלא תקין: User→Book→Hold→Loan→DeleteLoan→DeleteHold→DeleteBook→DeleteUser | כל אחד מהבאגים ב-2.11–2.16, 2.28–2.33, 2.56–2.58 ישבור נקודה אחרת ברצף המלא | רצף ה-happy-path "הסטנדרטי" ביותר של המערכת נשבר בכל נקודה — קריטי לבדיקת רגרסיה |
| 3.12 | יצירת 3 ספרים, 3 יוזרים, כל יוזר שואל ספר אחר, יוזר אחד מחזיר ולוקח ספר של יוזר אחר לאחר שהוחזר | הסרת בדיקת "Book is already loaned" (2.40) בשילוב עם timing של DELETE loan | ספר "יינגס" בין שני יוזרים בו-זמנית אם ה-DELETE וה-POST של loan חדש לא atomic |
| 3.13 | חיפוש (`GET /loans?userId=X&bookId=Y`) אחרי רצף ההשאלה/החזרה | באג 2.48 (פילטר bookId לא מצטבר על userId) | תוצאות חיפוש שגויות מוצגות למשתמש אחרי פעולות תקינות לגמרי |
| 3.14 | `/reset` באמצע רצף (איפוס בין תרחישי טסט) עם seed data חלקי (`users` בלבד, בלי books/loans/holds) | באג 2.1/2.3/2.4 ברענון חלקי | מצב "מלוכלך" בין טסטים — טסטים הבאים ברצף ייכשלו בגלל דליפת state |

## רמה 4 — באגים מרצפי קלט לא-הגיוניים / בסבירות נמוכה (Stress / Edge Sequences)

תרחישים אלה חוזרים על אותה פעולה שוב ושוב, או מבצעים סדר לא-טבעי (אך חוקי מבחינת ה-API) שיחשוף מצבי race / דליפת state / חוסר אידמפוטנטיות.

| # | תרחיש | באג פוטנציאלי | תוצאה |
|---|---|---|---|
| 4.1 | יצירת אותו יוזר (`POST /users` עם אותו id) פעמים רבות ברצף | הסרת/היחלשות בדיקת הכפילות (2.6) | ריבוי רשומות זהות ב-`users` — `user_exists` עדיין יעבוד (any) אך `search_users`/מחיקה יתנהגו לא צפוי (מחיקה אחת בלבד מתוך כמה כפילויות) |
| 4.2 | מחיקת אותו יוזר (`DELETE /users/<id>`) פעמים רבות ברציפות | חוסר idempotency אמיתי (הקוד הקיים כבר מטפל נכון ב-404 בשנייה) — שתילת באג שהופך את הבדיקה כך שהקריאה השנייה תזרוק 500 (למשל גישה ל-`user.get(...)` על `None`) | קריאה כפולה תקרוס במקום להחזיר 404 בעדינות |
| 4.3 | יצירה ומחיקה חוזרות של אותו hold id ב-loop מהיר (Create→Delete→Create→Delete... 50 פעם) | דליפת memory/רשימה לא מנוקה כראוי (למשל `holds.append` בלי לבדוק שההסרה הקודמת הצליחה, בשילוב 2.53) | לאחר X איטרציות, `holds` מכיל עותקים "רפאים" שחוסמים delete_book/delete_user |
| 4.4 | הרשמה (`POST /users`) ואז מחיקה (`DELETE`) ואז הרשמה **מיידית** עם אותו id אך `name` שונה | שיתוף state שגוי — שתילת cache/lookup שגוי ב-`user_exists` שמסתמך על רשימה לא מעודכנת | היוזר "החדש" נכשל ליצירה כי המערכת חושבת שהישן עדיין קיים |
| 4.5 | יצירת N holds לאותו bookId ע"י יוזרים שונים (תור המתנה ארוך), ואז מחיקת כולם בסדר הפוך מהיצירה (LIFO) | פילטר מחיקה שמניח סדר FIFO (למשל שימוש ב-`index` קבוע במקום סינון לפי id, כווריאציה של 2.56) | hold לא נכון נמחק כשסדר המחיקה שונה מסדר היצירה |
| 4.6 | `POST /loans` נכשל (ספר כבר מושאל) → נסיון שוב ושוב (retry loop) של אותה בקשה 100 פעם | פעולה לא-אידמפוטנטית שבטעות **כן** מוסיפה רשומה בכל ניסיון למרות כשל מדווח (atomicity break כמו 3.8) | ריבוי loans "כפולים" בפועל לאותו bookId למרות שה-API טוען שרק loan אחד נוצר |
| 4.7 | מחיקת ספר/יוזר לפני שמעולם נוצר (`DELETE /books/999`) חוזר על עצמו פעמים רבות | חריגה בטיפול ב-404 שצוברת side-effect שגוי (למשל לוגר/מונה גלובלי שגדל בלי בקרה — לא משפיע פונקציונלית אך רלוונטי לביצועים/DoS) | Log flooding / האטת המערכת תחת עומס בקשות שגויות חוזרות |
| 4.8 | `POST /reset` נקרא שוב ושוב תוך כדי שרשרת פעולות אחרות רצה (לא thread-safe מטבעה — Flask dev server single-threaded, אך רלוונטי אם ישונה) | שינוי שמוסיף thread לא בטוח בגישה ל-global lists בלי lock | Race condition בין reset לפעולות אחרות — התנהגות לא דטרמיניסטית |
| 4.9 | יצירת hold, ואז ביטול (`DELETE`) ואז יצירה **מחדש עם אותו `id` אך `bookId`/`userId` שונים לגמרי** חוזר על עצמו | שתילת "אופטימיזציה" שגויה ש-caches רשומת hold לפי id בלי לעדכן שדות בפועל (reuse אובייקט ישן) | Hold מכיל שילוב user/book שגוי — "רפאים" מהאיטרציה הקודמת |
| 4.10 | ניסיון ליצור loan, hold ומחיקת user לאותו userId **בו-זמנית / ברצף צפוף מאוד** (למשל 3 בקשות עוקבות בלי document שהמערכת לא thread-safe) | חוסר atomicity כללי סביב הבדיקות מול המאגר הגלובלי (`any(...)` ואז `.append(...)` ללא lock) | תנאי מרוץ קלאסי (TOCTOU — Time Of Check to Time Of Use): שני loans לאותו bookId יכולים להיווצר "בו-זמנית" אם הקוד ישונה להיות async/מקבילי |
| 4.11 | Delete user → Delete same user → Add user עם אותו id → Delete user שוב, בלולאה של עשרות פעמים | הצטברות state שגויה (זיכרון דולף) ב-`users` אם ה-remove מבוסס על ערך אובייקט (`users.remove(user)`) ולא על id, בשילוב מספר יוזרים "שווים" מבחינת dataclass equality | הסרת היוזר הלא נכון כשקיימים שני dict-ים זהים בתוכן אך עם id דומה שנוצרו-נמחקו-נוצרו |
| 4.12 | חיפוש (`GET /users?q=...`) עם query string ארוך/מיוחד (regex meta-characters, `%00`, אימוג'י) חוזר על עצמו | שתילת שינוי מ-`in` (substring) ל-`re.search` בלי escaping | Regex Injection / ReDoS פוטנציאלי בחיפוש |
| 4.13 | רצף: הוספת יוזר → הוספת אותו ספר N פעמים עם id שונה אך title זהה → חיפוש לפי title | אין קיים בעיה היום (id הוא המפתח הייחודי, לא title) — שתילת "תיקון" שגוי שמוסיף בטעות בדיקת ייחודיות על title | הוספת ספרים עם כותרות זהות (תרחיש לגיטימי — כמה עותקים) תיחסם בטעות |

## הערה מתודולוגית

- כל הבאגים לעיל הם **בעיה שניתן להכניס לקוד הקיים** (mutation), לא באגים שכבר קיימים במערכת בפועל.
- חלק מהבאגים ברמה 3–4 מבוססים גם על "חוסרים תפקודיים קיימים" במערכת (למשל: אין קשר לוגי אמיתי בין hold ל-loan, אין atomicity, אין thread-safety) — אלה **לא** נספרים כבאגים לשתילה בפני עצמם, אלא כ**הזדמנויות לשתול באג שמחמיר** התנהגות קיימת (המסומנות בפירוש בטבלה, ראו למשל 3.1, 3.2, 4.10).
- מומלץ להשתמש בטבלה זו כבסיס למטריצת Mutation Testing: לכל שורה — לשתול את הבאג, להריץ את חבילת הטסטים הקיימת, ולוודא שלפחות טסט אחד "תופס" (kill) את המוטציה. שורה שאף טסט לא תופס מצביעה על פער בכיסוי הבדיקות.
