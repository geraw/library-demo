The native model is still generated by the producer from its contract and JSON configuration. Its original gateway evidence collection remains part of that frozen toolkit package.

## Run

From a checkout of branch `natchan-work-v001` at the release commit supplied with the handoff:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force
& .\tools\natchan-work-v001\Invoke-Natchan-Work-v001.ps1
```

Parameters override the defaults without changing the pinned releases:

```powershell
& .\tools\natchan-work-v001\Invoke-Natchan-Work-v001.ps1 `
    -OriginalRepo 'C:\work\temp\vikunja_study' `
    -StudyRoot 'C:\work\temp\gitea_tse_study' `
    -ProvengoJar 'C:\work\temp\vikunja_tse_study\Provengo-2026-01-10.uber.jar' `
    -Seed 1
```

If a **closed outer model ZIP** already exists, analyze it without starting Docker, using Java, resetting the SUT or generating new traffic:

```powershell
& .\tools\natchan-work-v001\Invoke-Natchan-Work-v001.ps1 `
    -Package "$env:USERPROFILE\Downloads\v1-gitea-model-YYYYMMDD-HHMMSS.zip"
```

The existing-package mode still needs the existing local config for secret scanning and Git access to pinned tools. It does not assert that it personally observed the experiment. Bare inner review ZIPs are supported by Natchan itself, but not by this outer-package coordinator. `-Python` may name a specific Python executable. No `-AllowOtherJar`, `-NoReset`, harness fallback or manual dependency map is introduced.

## What happens

1. Verify the existing configuration, the frozen JAR and the baseline. Create an isolated integration directory under `<StudyRoot>\analysis\work-v001-<UTC time>-<suffix>`.
2. Fetch exact source checkouts. Copy only harmless `local.json` redaction preferences. Verify the producer manifest and run the 109 v004 wrapper tests.
3. Invoke `toolkit/v1/run/Run-Model.ps1` via Windows PowerShell with one seed and the existing config. The process actually invokes native Java/Provengo through the unchanged producer. Console progress is streamed; an integration heartbeat prints during otherwise silent periods.
4. Select exactly one newly closed outer model ZIP. Never select an older ZIP as fallback. Recheck secrets, inspect nested evidence availability and retain the original experiment status and native statuses.
5. Construct the existing `natchan-request/1` input with actual product version and archive SHA256; run v004 as a separate offline process. Verify its final result marker, wrapper version, process exit and artifact hashes.
6. Keep canonical local outputs unchanged. Export an explicitly sanitized copy alongside the unchanged evidence archive. Refresh copied artifact hashes and record original/exported hashes in `EXPORT_MANIFEST.json`. Run the pinned producer's existing nested-ZIP secret scanner on the entire share folder, then zip and copy it to `<StudyRoot>\upload`.

The producer itself still automatically runs its pinned **v003** analyzer at the end. Its old output remains separate. The coordinator then explicitly runs **v004**; this is deliberate preservation of the frozen producer, not an assertion that its internal analyzer pin has changed. The last `UPLOAD THIS FILE` line following `WORK_V001_STATUS` identifies the combined **v004 integration** deliverable.

## Input and output

Private local integration folder:

| File/folder | Meaning |
|---|---|
| `producer/`, `analyzer/` | Exact isolated source checkouts |
| `analysis-request.json` | Actual v004 request, with original archive hash and actual metadata |
| `output/` | Canonical analyzer outputs: result, findings, coverage, provenance, diagnostics, report and analysis |
| `evidence-check.json` | Counts of evidence records/format fields and recorded JAR/status metadata; not finding classification |
| `integration-status.json` | Experiment status, native-run status, analysis status/exit and coverage counts kept separately |
| `producer-console.private.log` | Local console; never added to the share export |
| Other local logs | Integrity, tests, analyzer and leak checks |
| `share/`, `natchan-work-v001-review.zip` | Allowlisted sanitized export and combined archive |

The combined ZIP contains the original evidence ZIP in `evidence/`, a portable analysis request and sanitized output copy in `analysis/`, status/availability summaries and `EXPORT_MANIFEST.json`. The portable request uses the embedded `sut.json`; it has no local repository path dependency. Reanalysis needs a fresh output directory. Do not upload the whole local integration directory or any credentials file. Original raw analysis bytes remain local; their hashes are retained in the export manifest.

The final terminal output is:

```text
INTEGRATION_STATUS <local status path>
WORK_V001_STATUS ANALYZED ANALYSIS=COMPLETE|PARTIAL
UPLOAD THIS FILE: <StudyRoot>\upload\work-v001-...-review.zip
```

`ANALYZED` means the coordinator processed recorded run evidence and produced the analysis/share output. It does not mean Provengo completed all scenarios, every evidence record is independently verified, or the SUT is correct. `NATIVE_PREFIX_RECORDED` recognizes completed, first-failure-stopped or time-limited native prefixes with the expected recorded JAR hash; it does not relabel them all as complete runs. Old-package mode uses `NOT_ASSERTED_EXISTING_PACKAGE`. A failed producer with no run evidence, an incomplete native execution or failed analysis returns integration exit 2; useful diagnostics may still be packaged. A secret-scan failure produces no new upload ZIP. A Ctrl+C interruption leaves a coordinator lock because producer cleanup may still be running; confirm the producer and SUT cleanup have ended before removing that lock. Do not launch a competing reset to recover it.

The analyzer's own COMPLETE/PARTIAL exit-0 policy and failure exit codes are unchanged. Findings and coverage come only from the analyzer. There are no expected finding counts in the request. Missing snapshot/readback/context evidence remains a gap. Reference IDs in different scopes are not equated to force the cloud sample's reported count.
